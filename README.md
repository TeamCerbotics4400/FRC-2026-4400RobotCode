## Overview

Robot code for the 2026 season. The robot is a swerve chassis with a fuel
handling system made up of an intake, a hopper and a shooter with a variable
hood, plus AprilTag vision for odometry correction.

The most important feature of this codebase is **dynamic shooting**: the robot
computes flywheel speed and hood angle in real time based on its distance to the
target, while also compensating for its own velocity (shoot-on-the-move). This
lets the robot score while the chassis is still moving instead of having to stop.

Main capabilities:

- Field-relative swerve drive with AprilTag odometry correction
- Distance-interpolated shooting with motion compensation
- Chassis auto-aim toward the target while the driver keeps translation control
- Autonomous routines with PathPlanner and NamedCommands
- Full logging through AdvantageKit with log replay
- Live tuning of PID gains and setpoints from SmartDashboard

## Architecture

### AdvantageKit IO Pattern

Every mechanism subsystem is split into three pieces. This allows swapping
hardware for a simulation without touching the logic, and makes logs
deterministically replayable.

```
Subsystem (logic)  ->  IO Interface  ->  Implementation (FX / Sim)
   Shooter.java        ShooterIO.java      ShooterFX.java
   Intake.java         IntakeIO.java       IntakeFX.java
   Hooper.java         HooperIO.java       HooperFX.java
```

Each IO interface declares an inputs class annotated with `@AutoLog`, which
automatically generates the `...InputsAutoLogged` class used to record every
sensor value:

```java
@AutoLog
public static class ShooterInputs {
  public double shooterRPMs = 0.0;
  public Rotation2d hoodAngle = Rotation2d.kZero;
  // ...
}
```

The pattern inside every `periodic()` is always the same: read hardware, log it,
then act on the already-logged values.

```java
@Override
public void periodic() {
  io.updateInputs(inputs);
  Logger.processInputs("Shooter", inputs);
  // ... logic using inputs
}
```

### Lifecycle

```
Robot() (constructor)
  ├─ Configures log receivers (WPILOGWriter, NT4Publisher)
  ├─ Creates RobotContainer (subsystems, bindings, autos)
  └─ Logger.start()
        ↓
robotPeriodic() every 20 ms
  ├─ Publishes distances to hub/target
  ├─ HootAutoReplay.update()
  ├─ CommandScheduler.run()  ->  each subsystem periodic()
  └─ ShiftTimer.updateDashboard()
        ↓
autonomousInit()  ->  schedules the auto from the chooser
autonomousPeriodic()  ->  clears shooting parameters every cycle
```

Important note: `ShotCalculator` caches its parameters per cycle, and
`autonomousPeriodic()` calls `clearShootingParameters()` to force a recompute.
In teleop, the one clearing that cache is `OrbitinWithMovement`.

## Subsystems

### Swerve (`subsystems/Swerve/`)

`CommandSwerveDrivetrain` extends `TunerSwerveDrivetrain` (generated by Phoenix
Tuner X) and implements `Subsystem`.

Responsibilities:

- Field-centric control in teleop
- PathPlanner integration through `AutoBuilder.configure(...)`
- Odometry correction from vision measurements
- SysId routines for characterization (translation, steer, rotation)
- Operator perspective per alliance (0 degrees blue, 180 degrees red)

Path following gains (`PPHolonomicDriveController`):

```
Translation: kP = 5.1
Rotation:    kP = 5.0
```

Relevant methods:

| Method | Description |
|--------|-------------|
| `goToPose(pose)` | On-the-fly pathfinding to a pose |
| `isAligned()` | Compares current heading against the ShotCalculator angle |
| `isRobotMoving()` | True when lateral velocity exceeds 0.25 m/s |
| `applyAutoAimOverride(...)` | Overrides PathPlanner rotation feedback during auto |
| `addVisionMeasurement(...)` | Feeds a vision pose into the Kalman filter |
| `xBrakeCommand()` | X formation against defense |

In simulation it starts a `Notifier` at 2 ms that updates the simulated state and
maintains a parallel `SwerveDriveOdometry`.

### Shooter (`subsystems/Shooter/`)

Hardware: four TalonFX flywheels and one hood motor.

```
ID 30  Upper Right  (LEADER)
ID 31  Down Right   (Follower, Aligned)
ID 32  Upper Left   (Follower, Opposed)
ID 33  Down Left    (Follower, Opposed)
ID 34  Hood
```

Only motor 30 receives commands; the other three follow it. The left side spins
opposite due to the mechanical layout.

Configuration (Slot 1, Motion Magic Velocity with FOC):

```
kS = 0.3     kV = 0.5     kA = 0.065
kP = 55.0    kI = 0       kD = 0
MotionMagicAcceleration = 1500
MotionMagicJerk         = 4000
Supply current limit    = 50 A
Neutral mode            = Coast
```

The hood uses `MotionMagicVoltage` and converts degrees to motor rotations with
`kHoodDegreesPerMotorRotation = 5.741626`.

The `Shooter` subsystem works with **suppliers**: `shootAndMoveLoLVoid()` does not
set a fixed value, it installs two functions that query `ShotCalculator` on every
`periodic()` and update RPM and angle. That is why the shot adapts by itself
while the robot moves.

```java
public void shootAndMoveLoLVoid() {
  flywheelSpeedSupplier = () -> ShotCalculator.getInstance().getParameters().flywheelSpeed() + offSet;
  hoodAngleSupplier     = () -> ShotCalculator.getInstance().getParameters().hoodAngle();
}
```

`safeHood()` clears both suppliers, sends the hood to 20 degrees and cuts voltage.
The `offSet` field is a manual RPM trim exposed on SmartDashboard.

### Intake (`subsystems/Intake/`)

Hardware:

```
ID 22  Pivot
ID 21  Left roller
ID 20  Right roller
```

The pivot is driven by a `ProfiledPIDController` plus a `SimpleMotorFeedforward`,
evaluated in the subsystem `periodic()` while `enablePID` is active:

```
kP = 100    kI = 0    kD = 0
kS = 0      kV = 200  kA = 0
Normal profile: maxVelocity = 300, maxAcceleration = 300
Slow profile:   middleVel = 50,   middXLR8tion = 50
```

Target positions: `IntakeDeployed = 0.24`, `MiddleIntake = 0.18`.

Rollers spin in opposite directions (`setIntakeLeftVoltage(v)` and
`setIntakeRightVoltage(-v)`). The pivot current limit is changed on the fly
depending on the command: 80 A for `setPivotPosition`, 60 A for `deployIntake`.

`shakeIntakeCommand(pos)` deploys, waits and retracts to shake the fuel loose and
keep it from jamming at the entry.

### Hooper (`subsystems/Hooper/`)

Hardware actually instantiated:

```
ID 40  Upper Roller (leader, 60 A stator limit)
ID 42  Lower Roller (Follower of 40, Opposed)
ID 41  Parrilla     (independent, 80 A stator limit)
```

`Constants.HooperContants` also defines `FLRollerID = 43`, but that motor is not
instantiated in `HooperFX`.

Control runs through `MotionMagicVelocityVoltage` with FOC, or through direct
voltage using `setVoltage(voltageUpper, voltagedown)`, where the second parameter
drives the parrilla.

Signals from motor 40 (velocity, voltage, current) are refreshed at **250 Hz** to
enable fast jam detection.

### Vision (`subsystems/Vision/`)

Two Limelight cameras configured with 3D offsets relative to the robot center:

- `limelight-tags`: main camera, rear mounted
- `limelight-lateral`: side camera (created and configured, but its pose update
  is commented out in `periodic()`)

Estimation strategy:

- Robot **disabled**: MegaTag1 (does not depend on the gyro)
- Robot **enabled**: MegaTag2 (uses robot orientation, more stable)

Quality filters applied before accepting a measurement:

```
avgTagDist < 4.0 m
tagCount > 0
minTagAmbiguity < 0.3
```

Only when all three pass does it call `m_drive.addVisionMeasurement(...)`.

The `periodic()` also walks the neural classifier results looking for objects of
class `"fuel"` (the associated action is still empty).

## Shooting Logic (ShotCalculator)

This is the most elaborate part of the codebase. `ShotCalculator` is a singleton
that produces a `ShootingParameters` record:

```java
record ShootingParameters(
    boolean isValid,
    Rotation2d turretAngle,
    double turretVelocity,
    double hoodAngle,
    double hoodVelocity,
    double flywheelSpeed)
```

Calculation process:

1. **Latency compensation:** projects the current pose forward by
   `phaseDelay = 0.03 s` using robot velocity.
2. **Dynamic target:** `FieldUtil.getDynamicTarget()` decides whether to aim at
   the hub or at the bumps based on field position and alliance.
3. **Iterative lookahead:** repeats the time-of-flight and robot-displacement
   calculation 20 times to converge on the point to aim at when shooting on the
   move.
4. **Interpolation:** uses the converged distance to look up RPM and hood angle
   in `InterpolatingTreeMap` tables, split into near and far.
5. **Angular velocities:** differentiates and filters (0.1 s moving average) the
   angle changes to feed the auto-aim feedforward.
6. **Validity:** the shot is marked valid only when the distance falls between
   `minDistance = 1.4 m` and `maxDistance = 15 m`.

Calibration tables (approximate ranges):

| Table | Range | Contents |
|-------|-------|----------|
| `shotHoodAngleMap` | 1.8 - 4.8 m | 20 to 32.5 degrees |
| `shotFlywheelSpeedMap` | 1.9 - 4.8 m | 1700 to 2350 RPM |
| `shotHoodAngleMapFar` | 6 - 13 m | 40 degrees (feed) |
| `shotFlywheelSpeedMapFar` | 6 - 13 m | 2000 to 2900 RPM |
| `shotTOFMap` | 1.8 - 4.2 m | Time of flight 0.96 to 1.17 s |

The result is cached per cycle; `clearShootingParameters()` must be called to
recompute it.

## Commands and Controls

### DriveCommand

Default chassis command. Applies a `SlewRateLimiter` on all three axes, a 10
percent deadband, and field-centric control with `OpenLoopVoltage`. Maximum
angular rate: 1 rotation per second.

### OrbitinWithMovement

Auto-aim: the driver keeps (scaled down) translation control while a rotation PID
(`kP = 5`, continuous input) turns the robot toward the target. It adds
`turretVelocity` as feedforward to track moving targets. It aims at
`turretAngle - 180` because the shooter is mounted on the rear of the robot.

### ShootUntilIsReady

Spins up the shooter and **only feeds the hopper once both conditions are met**:
the chassis within 3 degrees of the target angle and the flywheel within 20 RPM
of its setpoint. This prevents wasted shots.

### Control map (Xbox, port 0)

| Control | Action |
|---------|--------|
| Left stick | Field-centric translation |
| Right stick X | Rotation |
| Right bumper | Deploy intake at 12 V (retracts on release) |
| Left bumper | Auto-aim + `ShootUntilIsReady` + shake intake |
| Left trigger | Auto-aim + `smartShootCommand` + intake deployed |
| Y | Flywheel to 2000 RPM + shake intake |
| B | Eject: intake and hopper in reverse (-12 V) |
| X | `ResetPivot` (intake homing) |
| Start | Reset field-centric heading based on alliance |

Releasing the shooting buttons runs the cleanup: stop hopper, send the hood to a
safe position and reset the pivot.

## Autonomous

### Structure

`AutoCommand` is the abstract base class; it extends `SequentialCommandGroup` and
forces exposing the path so it can be previewed:

```java
public abstract class AutoCommand extends SequentialCommandGroup {
  public abstract List<Pose2d> getAllPathPoses();
  public abstract Pose2d getStartingPose();
}
```

Each auto loads its `.path` files for the preview and wraps a `PathPlannerAuto`
with the exact name of the `.auto` file. Loading is wrapped in try/catch and
reports to the Driver Station if a file is missing instead of crashing.

### Autos in the selector

| Chooser option | Class |
|----------------|-------|
| Optimizes 1 Cicle + Depot (default) | `LagunaAuto` |
| Laguna + 1678 Auto | `LCAutoLeft` |
| Laguna + 1678 Auto Right | `LCAutoRight` |
| SecondPickAuto | `SecondPickAuto` |
| AUTO | `Auto` |

The chooser also publishes a `Field2d` named "Auto Preview" that draws the
selected trajectory before the match.

### NamedCommands

Registered in `RobotContainer.enableNamedCommands()` so they can be used inside
PathPlanner `.auto` files:

```
IntakeCommand        StopIntaking        StopShooter
ShootandMove         ActivateHopper      DisableHopper
SmartShootCommand    SmartShootCommand2P ShakeIntake
AutoAlign            ReverseHopper
```

### Warmup

The `RobotContainer` constructor schedules `PathfindingCommand.warmupCommand()`
and `FollowPathCommand.warmupCommand()` to force JVM class loading and avoid the
first-path delay during a match.

## Utilities

### RobotState

Read-only singleton over the drivetrain. It does not run its own odometry: it
reads what Phoenix already computes. Requires a one-time `setDrivetrain()` call
from `RobotContainer`.

```java
RobotState.getInstance().getEstimatedPose();
RobotState.getInstance().getFieldRelativeVelocity();
RobotState.getInstance().getDistanceToAllianceHub();
RobotState.getInstance().atOrbitAngle(toleranceDeg, targetAngle);
```

### FieldUtil

Picks the target based on the field zone: if the robot is in the shooting zone
(x below 3.8 on blue, above 12.0 on red) it aims at the hub; otherwise it aims at
the upper or lower bump depending on the Y coordinate.

### FieldConstants

Official field geometry taken from the AprilTag layout: hub dimensions, heights,
corners and reference points. It is the source of truth for 3D calculations. The
hub sits at 72 inches (1.83 m).

### AllianceFlipUtil

Mirrors poses and translations between alliances so constants are not duplicated.

### LocalADStarAK

Reimplementation of PathPlanner's AD* pathfinder made AdvantageKit-compatible:
instead of running the algorithm during replay, it records its inputs and outputs
so the log replays deterministically.

### ShiftTimer

State machine based on remaining match time, used to split strategy into shifts:

```
SHIFT1  from 2:10      SHIFT4  from 0:55
SHIFT2  from 1:45      ENDGAME from 0:30
SHIFT3  from 1:20
```

It also reads the `GameSpecificMessage` to know which alliance won auto.

## Logging and Telemetry

### AdvantageKit

- **On the real robot:** `WPILOGWriter` to USB (`/U/logs`) plus `NT4Publisher`
- **In simulation:** `NT4Publisher` plus `WPILOGWriter` to the working directory
- **HootAutoReplay:** records timestamps and joystick data to replay the match
- **Metadata:** the build `GIT_SHA` is recorded so you know which code ran

### Recorded outputs

```
/AdvantageKit/RealOutputs/
├── Swerve/ActivePath, TargetPathPose
├── Drive/OdometryPose, TargetStates, MeasuredStates, MeasuredSpeeds
├── Drive/Module0..3
```

`Telemetry.java` additionally publishes swerve state to SignalLogger (CTRE hoot

Live-editable values: `Shooter/DashRPMs`, `Shooter/DashHoodAngle`,

`Drive/Is Aligned`, `Drive/Is Drive Moving`, `Intake/inSensor`.

The file `src/main/deploy/elastic-layout.json` defines the Elastic dashboard
layout for the Driver Station.

  Since those run as Followers the impact is minor, but keep it in mind when
  changing gains.

## Conventions

- **Formatting:** google-java-format through Spotless. Run
  `./gradlew spotlessApply` before every commit; the build validates formatting.
- **Naming:** `m_` for subsystem members, `PascalCase` for classes, `camelCase`
  for methods and variables.
- **New subsystems:** follow the IO pattern (interface + `@AutoLog` + one
  implementation per hardware target). Never touch a motor directly from a
  command.
- **Commands:** anything that moves a mechanism must declare its requirements
  with `addRequirements(...)` so the scheduler can avoid conflicts.
- **Constants:** no magic numbers inside subsystems; everything belongs in
  `Constants.java`.
- **Logging:** record inputs with `Logger.processInputs(...)` and computed
  outputs with `Logger.recordOutput(...)`.
